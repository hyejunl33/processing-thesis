# 졸업논문 프로젝트 아이디어 검토

> 작성일: 2026-11-12
> 제약: Processing 4 (Java mode)로 구현하고 배포할 것.
> 전제: 광주교육대학교 컴퓨터교육과 졸업논문. 2027년 2월 졸업 예정. 2026학년도 2학기 졸업논문 심사 신청 기간(2026-11-16)에 계획서 제출.

## 0. 아이디어를 고르는 기준

1. **Processing이 장식이 아니라 논리일 것.** 핵심 로직(실행, 비전, 서버, 시각화)이 Processing 스케치 안에 있어야 한다.
2. **교육적 효과를 측정할 수 있을 것.** 최소한 사전·사후 개념 검사, 과제 수행 로그, 인터뷰 중 하나는 있어야 한다.
3. **기존 경력이 논문의 방법론으로 이어질 것.** LLM 하네싱, 멀티모달 파이프라인, 검증·실패 분석, 배포 경험이 프로젝트의 구조에 드러나야 한다.
4. **한 학기에 끝낼 수 있을 것.** 데모는 6~8주, 적용·분석은 6~8주로 나눌 수 있어야 한다.
5. **교실에서 설명 가능할 것.** 교수님과 현장 교사에게 "왜 이게 초등교육에 필요한가"를 30초 안에 말할 수 있어야 한다.

## 1. TraceCraft — 코드의 결과가 아니라 과정을 보는 코딩 학습 환경

**가칭:** TraceCraft  
**한 줄 정의:** LLM이 생성한 Processing 코드를 초등학생이 그대로 복사하지 않고, 실행 과정을 추적·설명·수정하게 만드는 학습 환경.

### 문제

LLM 코딩 도구는 초보자에게 "작동하는 결과물"을 즉시 준다. 하지만 초등 프로그래밍 교육의 목표는 결과물이 아니라 **순서, 반복, 변수, 좌표, 조건**의 이해다. 결과만 보면 학습자는 "코드를 이해했다"는 착각(illusion of competence)을 하게 되고, 코드를 조금 바꾸면 무너진다. 이른바 코드슬롭(code slop)이다.

### 연구 질문

- RQ1. LLM 보조 코딩에서 **실행 추적 시각화**는 초등학생의 반복·변수·좌표 개념 이해를 향상시키는가?
- RQ2. 실행 추적은 **LLM 의존도**를 낮추는가? (전체 재생성 vs 부분 수정, 설명 정확도, 자기 수정 횟수)
- RQ3. 학생들이 보이는 **오개념 패턴**은 무엇이며, 교사는 그 패턴을 어떻게 활용할 수 있는가?

### 개입(Intervention)

1. 학생이 자연어로 목표를 말한다. ("밤하늘에 반짝이는 별을 그려줘")
2. 시스템이 **제한된 Processing 문법**(도형, 색, 변수, for, if, random) 안에서 코드를 생성한다.
3. 실행 전에 "실행 계획"을 보여준다. (반복 횟수, 좌표 계산, 난수 시드)
4. 실행 후 **타임라인**으로 각 도형이 언제·어떤 변수로 그려졌는지 보여준다. 학생은 슬라이더로 시간을 되돌리고, 변수를 바꾸고, 코드와 캔버스를 동시에 본다.
5. 학생은 "이 별이 반짝이게 하는 줄은 어디인가?" 같은 **설명·수정 과제**를 수행한다. 전체 코드를 다시 생성하는 버튼은 제한하거나, 설명을 통과해야 사용할 수 있게 한다.
6. 교사 대시보드에는 학생별 오개념(예: `for` 대신 도형 복붙, 좌표계 혼동, `setup`/`draw` 혼동)이 집계된다.

### Processing의 역할

- **실행 엔진:** `PApplet`/`PGraphics`로 코드를 실행하고 프레임을 캡처.
- **추적기:** 그리기 호출, 루프 반복, 변수 변화, 난수 시드를 이벤트로 기록.
- **시각화:** 코드 패널, 캔버스, 타임라인, 변수 인스펙터를 한 화면에 렌더링.
- **로컬 서버:** LLM 프록시, 코드 검증, 실행 샌드박스, 로그 저장을 Processing 앱 안에서 수행.
- **배포:** Processing export로 macOS/Windows/Linux 앱, GitHub Releases, 필요 시 Docker + Xvfb.

### 아키텍처 초안

```
[Processing App]
 ├─ Editor / Canvas / Timeline (ControlP5 or custom UI)
 ├─ Code Validator (AST whitelist, loop bound, no file/network)
 ├─ Sandbox Runner (separate process or thread, timeout, seeded random)
 ├─ Trace Recorder (JSON Lines: step, line, vars, draw call, timestamp)
 ├─ LLM Orchestrator (prompt → code → validate → repair → cache)
 └─ Local HTTP Server (optional teacher dashboard / telemetry)
```

### 평가 설계

- 대상: 초등 5~6학년 2개 학급(또는 예비교사 30명). 가능하면 실습 학교와 연계.
- 설계: 사전·사후 개념 검사 + 통제/실험 집단(출력만 보기 vs 추적 보기) + 수행 로그 + 인터뷰.
- 측정: 반복·변수·좌표 개념 점수, 코드 설명 과제 정확도, 재생성/수정 비율, 인지부하(CL), 사용성(SUS).
- 분석: 대응표본/독립표본 비교, 로그 시퀀스 분석, 오개념 코딩.

### 경력 연결

- 뤼튼의 **하네싱**: 스펙 → 생성 → 검증 → 실패 시 재시도 → QA.
- LLM 파이프라인의 **고정 스키마, 캐시, 폴백, 평가 하네스** 경험.
- 부스트캠프의 **실험 설계와 지표** 경험.
- "코드슬롭을 어떻게 학습 자산으로 바꿀 것인가"라는 문제의식 자체가 논문의 동기.

### 리스크

- 코드 실행 샌드박스와 추적 계측이 생각보다 어렵다. → 1차는 자체 인터프리터(제한 DSL), 2차는 Java 소스 변환으로 확장.
- LLM API 비용/네트워크 의존. → 캐시된 생성 결과와 오프라인 모드 제공.
- 학생 대상 연구윤리/동의. → 예비교사 대상 파일럿을 먼저 하고, 초등 적용은 학교 협조 후 진행.

### 한 학기 범위 제안

- 4주: 문헌/선행 도구 분석, DSL·추적 이벤트 스키마 설계.
- 6주: Processing 프로토타입(에디터·캔버스·타임라인·샌드박스).
- 4주: LLM 생성·검증·캐시, 오개념 규칙.
- 6주: 파일럿 1회 + 본 적용 1회, 분석.
- 4주: 논문 작성.

## 2. Classroom Canvas — Processing 하나로 교실 서버까지

**가칭:** Classroom Canvas  
**한 줄 정의:** 교사 노트북(또는 라즈베리파이)에서 Processing 앱 하나로 도는, 클라우드 없는 실시간 과정중심 형성평가 시스템.

### 문제

교실에는 1인 1태블릿이 있지만, 실제 사용은 "활동 사진 찍어서 학부모에게 공유" 수준에 머물러 있다. 기존 클래스룸 도구는 제출 여부와 정답만 모은다. 교사가 수업 중에 필요한 것은 **학생이 어디서 막히는지, 얼마나 확신하는지, 어떤 오개념이 퍼지는지**에 대한 실시간 신호다. 또한 학교 네트워크는 외부 클라우드가 막히거나 느릴 수 있고, 학생 개인정보를 외부로 보내는 것도 부담이다.

### 연구 질문

- RQ1. 실시간 과정중심 대시보드는 교사의 **noticing**과 즉각적 수업 결정을 바꾸는가?
- RQ2. 오프라인 엣지 서버는 교실 규모에서 **지연·안정성·설치 용이성**을 만족하는가?
- RQ3. 학생들은 자신의 과정이 시각화되는 것을 어떻게 경험하는가?

### 개입

- 교사가 Processing 앱을 실행하면 QR 코드가 뜬다. 학생은 교실 LAN으로 접속해 답/확신도/중간 과정을 제출한다.
- 교사 화면에는 ① 참여 현황, ② 답 분포, ③ 확신도 지도, ④ 수정·머뭇거림 패턴, ⑤ 교사가 주목할 응답이 실시간으로 표시된다.
- 교사는 응답을 "스포트라이트"해서 다음 발문을 던지고, 수업 후에는 기록을 내보낸다.
- 데이터는 교사 기기 밖으로 나가지 않는다.

### Processing의 역할

- **HTTP 서버:** `processing.net.Server` 또는 `com.sun.net.httpserver`로 학생용 페이지/API 제공.
- **실시간 채널:** WebSocket 또는 SSE(가능하면 라이브러리, 불가능하면 long-polling).
- **저장:** SQLite(JDBC) 또는 JSON Lines. 수업 세션 단위로 익명화.
- **대시보드:** Processing의 강점인 실시간 2D 시각화로 참여/오개념/흐름을 표현.
- **배포:** GitHub Releases(앱), Docker 이미지(서버), 라즈베리파이 설치 스크립트. GitHub Actions로 빌드.

### 아키텍처 초안

```
[Teacher Laptop / Raspberry Pi]
 └─ Processing Sketch
     ├─ HTTP Server (student page, submit API)
     ├─ Session Store (SQLite: events, responses, revisions)
     ├─ Aggregator (windowed counts, confidence map, clusters)
     ├─ Dashboard Renderer (P2D)
     └─ Export (CSV/JSON, lesson report)

[Student Device]
 └─ Browser (QR → static page, no install)
```

### 평가 설계

- 대상: 1~2명의 현직/예비 교사, 1~2개 학급.
- 설계: 디자인 기반 연구(설계 → 적용 → 성찰 → 재설계) + 수업 영상/자극 회상 인터뷰.
- 측정: 대시보드 사용 로그, 교사의 발문/결정 변화, 학생 응답 지연·수정률, SUS, 네트워크 지연.
- 분석: 질적 코딩 + 기술 통계.

### 경력 연결

- 뤼튼의 **이벤트 스키마 → 집계 → 운영 대시보드** 경험.
- Airflow/DBT식 파이프라인 사고를 교실 규모로 축소.
- "클라우드 없이, 교사가 소유하는 AX"라는 배포 철학.
- 실습에서 본 "태블릿은 사진첩" 문제의 직접적 해결.

### 리스크

- 기존 클래스룸 response system과 차별화가 약할 수 있다. → 정답이 아니라 **과정 데이터**(확신도, 수정, 머뭇거림)와 **교사 noticing**에 초점.
- 학교 네트워크/기기 정책. → 오프라인 데모와 핫스팟 모드 준비.
- HTTP 서버를 Processing으로 직접 구현하는 삽질. → `processing.net.Server`로 시작하고, 필요하면 JDK HttpServer.

### 한 학기 범위 제안

- 3주: 요구 분석(교사 인터뷰), 이벤트 스키마, 프로토콜 설계.
- 6주: 서버·대시보드·학생 페이지 프로토타입.
- 4주: 교실 파일럿 1회, 로그/인터뷰 분석.
- 4주: 개선·2차 적용.
- 4주: 논문 작성.

## 3. Tangible Processing — 인쇄한 카드와 웹캠으로 만드는 탠저블 코딩

**가칭:** Tangible Processing  
**한 줄 정의:** 특수 하드웨어 없이, 인쇄한 명령 카드와 웹캠만으로 초등학생이 손으로 프로그램을 조립하는 Processing 기반 탠저블 프로그래밍 환경.

### 문제

구체적 조작기에 있는 초등학생에게는 화면 속 블록을 드래그하는 것보다 **실제 물체를 조작하는 것**이 유의미하다. 하지만 상용 탠저블 코딩 교구는 비싸고, 특정 태블릿/카메라에 묶이며, 교사가 수정하기 어렵다. 또한 교실의 태블릿은 "사진첩" 이상으로 쓰이지 않는 경우가 많다.

### 연구 질문

- RQ1. 탠저블 카드 조작은 화면 기반 블록 코딩보다 **순서·반복 개념** 습득에 효과적인가?
- RQ2. 저가 웹캠+인쇄 카드 환경은 교실에서 충분히 **견고하고 사용 가능**한가?
- RQ3. 학생들이 카드를 재배치하며 보이는 **디버깅 사고**는 어떤가?

### 개입

- 학생은 명령 카드(앞으로, 회전, 반복 시작/끝, 색, 펜)를 책상에 늘어놓는다.
- 웹캠이 카드의 ArUco/색 마커를 인식하고, Processing이 순서를 해석해 거북이를 움직인다.
- 잘못된 순서/빠진 카드/겹친 카드에 대해 즉각적인 시각 피드백을 준다.
- 학생은 카드를 다시 배열해 디버깅한다. 교사는 활동을 관찰하고, 시스템은 카드 배열 이벤트를 기록한다.

### Processing의 역할

- **비전:** OpenCV(JavaCV)로 마커 검출, 원근 보정, 카드 ID/위치/회전 추정.
- **언어:** 카드 시퀀스 → 프로그램 AST → 인터프리터.
- **실행/렌더링:** 거북이 그래픽, 경로, 오류 메시지, 활동 기록.
- **배포:** 웹캠이 달린 노트북에서 도는 단일 앱. 오프라인.

### 아키텍처 초안

```
[Webcam] → [Processing + OpenCV]
             ├─ Marker Detector (ArUco / color + shape)
             ├─ Layout Normalizer (desk ROI, perspective)
             ├─ Token Sequence Parser
             ├─ Turtle Interpreter (step, turn, repeat, pen)
             ├─ Renderer (canvas + card overlays + feedback)
             └─ Event Logger (card moves, program runs, errors)
```

### 평가 설계

- 대상: 초등 3~4학년 1~2개 학급.
- 설계: 사전·사후 CT 검사 + 통제/실험(화면 블록 vs 탠저블) + 활동 영상/인터뷰.
- 측정: 순서·반복 문항 점수, 과제 완수 시간, 오류 수정 횟수, 몰입/흥미, 교사 사용성.
- 분석: 혼합연구.

### 경력 연결

- 부스트캠프/뤼튼의 **비전 파이프라인**(검출, 전처리, 임계값, 오류 분석) 경험.
- "교실의 태블릿은 사진첩"이라는 실습 관찰과 "구체적 조작기"라는 교육학적 근거.
- 하드웨어 없이 소프트웨어만으로 물리적 조작감을 만드는 **HCI/엣지 컴퓨팅** 포트폴리오.

### 리스크

- 상용 탠저블 코딩(Osmo, Tern 등)과의 차별화 필요. → "인쇄물+웹캠+오픈소스+교사 수정 가능"으로 포지셔닝.
- 조명/가림/카메라 각도에 따른 인식 실패. → ArUco + 색 보조, 캘리브레이션 UI, 실패 시 수동 보정.
- 학생 대상 연구윤리/학교 협조.

### 한 학기 범위 제안

- 4주: 선행 탠저블 코딩 분석, 카드 문법/마커 설계.
- 6주: 비전·인터프리터·렌더러 프로토타입.
- 4주: 교실 파일럿, 인식 실패/오류 분석.
- 4주: 개선·2차 적용.
- 4주: 논문 작성.

## 4. SafeCanvas — AI 생성 이미지를 검수하는 눈을 기르는 시각 QA 콘솔

**가칭:** SafeCanvas  
**한 줄 정의:** 생성형 AI 이미지의 안전성·저작권·편향 신호를 시각적으로 보여주고, 예비교사/학생이 직접 검수 판단을 내리게 하는 Processing 기반 AI 리터러시 도구.

### 문제

생성형 AI 이미지는 교실 자료로 쉽게 쓰이지만, 교사는 그 이미지가 안전한지, 저작권을 침해하는지, 특정 집단을 왜곡하는지 판단하기 어렵다. 기존 도구는 "유해/안전" 이진 분류만 주고, 왜 그런지 설명하지 않는다. AI 리터러시 교육에는 **판단의 근거를 보는 연습**이 필요하다.

### 연구 질문

- RQ1. 시각 QA 콘솔은 예비교사의 AI 이미지 위험 탐지 정확도와 **calibration(자신감-정확도 일치)** 을 향상시키는가?
- RQ2. 어떤 시각 신호(텍스트 넘침, 얼굴 비율, 브랜드 유사도, 피부 노출, 메타데이터)가 판단에 가장 유용한가?
- RQ3. 검수 경험이 생성형 AI에 대한 신뢰/불신 태도에 어떤 영향을 주는가?

### 개입

- AI 생성 이미지 그리드와 함께, ① OCR 텍스트 오버플로, ② 얼굴/신체 비율, ③ 브랜드/캐릭터 유사도(pHash/CLIP), ④ 안전 범주, ⑤ 출처 메타데이터를 오버레이로 보여준다.
- 사용자는 각 이미지를 "사용 가능/수정 필요/사용 불가"로 판정하고 근거를 선택한다.
- 시스템은 판정과 신호의 불일치를 기록하고, 피드백을 제공한다.
- 수업 후 자신의 판정 로그를 돌아보며 "내가 놓친 신호"를 확인한다.

### Processing의 역할

- **이미지 분석:** OpenCV/JavaCV(얼굴, 색, 경계), Tesseract OCR, pHash, 필요 시 CLIP 임베딩(ONNX Runtime Java).
- **UI:** 이미지 그리드, 오버레이, 판정 패널, 로그/리포트.
- **백엔드 로직:** 검출기 파이프라인, 규칙 엔진, 신뢰도 집계, 감사 로그.
- **배포:** 데스크톱 앱. 분석 결과를 캐시해 오프라인에서도 동작.

### 아키텍처 초안

```
[Image Set] → [Processing]
                ├─ Detectors (OCR, face, skin ratio, pHash, metadata)
                ├─ Rule Engine (safe / needs edit / unsafe + reasons)
                ├─ Review UI (grid, overlays, judgment, confidence)
                ├─ Audit Log (judgment, signals, time, rationale)
                └─ Report Export (CSV/PDF-ish)
```

### 평가 설계

- 대상: 예비교사 30명(접근 쉬움), 가능하면 현직 교사.
- 설계: 사전·사후 탐지 과제 + calibration + 인터뷰 + 사용성.
- 측정: 탐지 정확도, 오탐/미탐, 자신감-정확도 차이, 판단 근거의 질, SUS.
- 분석: 대응표본, 혼합연구.

### 경력 연결

- 뤼튼의 **안전성 필터, IP 침해 탐지, 이미지 검색/렌더링, QA** 경험을 교육용으로 전환.
- "FN 0, 오탐 87.8% 감소" 같은 실무 지표를 교육적 판단 지표로 재해석.
- 멀티모달 파이프라인/검증 경험.

### 리스크

- 회사 프로젝트의 축소판처럼 보일 수 있다. → 교육적 연구 질문(calibration, AI 리터러시)을 전면에.
- 의존 라이브러리가 많다. → 1차는 정적 분석 + pHash/OCR, 2차에 얼굴/CLIP.
- 이미지 저작권/초상권. → 공개 데이터셋/직접 생성 이미지 사용, 민감 이미지 배제.

### 한 학기 범위 제안

- 4주: AI 리터러시 문헌, 신호/규칙 설계, 데이터셋 구성.
- 6주: 분석 파이프라인 + 검수 UI 프로토타입.
- 4주: 예비교사 파일럿, 신호 유용성 분석.
- 4주: 개선·본 적용.
- 4주: 논문 작성.

## 6. 추천

### 1순위: TraceCraft

- "코드슬롭"이라는 현재의 문제의식과 뤼튼/부스트캠프에서 쌓은 LLM 하네싱 경력이 논문의 방법론과 정면으로 만난다.
- Processing이 단순 렌더러가 아니라 **실행 엔진·추적기·샌드박스**로 쓰이므로 "Processing을 억지로 쓴 프로젝트"가 아니다.
- 졸업 후 포트폴리오로도 가장 강하다. (LLM + 교육 + 시스템 + 평가)
- 단, 실행 계측/샌드박스가 가장 어려운 부분이므로, 1차는 제한 DSL 인터프리터로 범위를 줄여야 한다.

### 2순위: Classroom Canvas

- 가장 안전하게 학기 안에 끝낼 수 있고, "Processing으로 백엔드와 배포까지"라는 요구를 가장 직접적으로 만족한다.
- 교실 적용/교사 인터뷰가 상대적으로 쉽고, 실습 학교와 연결하기 좋다.
- 다만 "또 하나의 클릭커"로 보이지 않도록 **과정 데이터와 교사 noticing**이라는 연구 질문을 날카롭게 세워야 한다.

### 3순위: Tangible Processing

- 교육학적 근거(구체적 조작기)와 실습 관찰이 가장 강하게 연결되고, 데모 임팩트가 크다.
- 비전 파이프라인 경험을 살릴 수 있지만, LLM/데이터 경력은 상대적으로 덜 드러난다.
- 인식 견고성과 교실 하드웨어 변수가 리스크.

### 4순위: SafeCanvas

- 뤼튼 경력과 가장 직접적으로 연결되지만, 회사 업무의 축소판으로 보일 위험이 있다.
- 예비교사 대상 연구는 접근성이 좋고, AI 리터러시라는 교육적 프레임도 설득력 있다.
- 분석 파이프라인의 dependency가 많아 1학기에는 범위를 좁혀야 한다.
